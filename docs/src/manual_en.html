NetBox ISC DHCP – manual

Plugin for NetBox that builds the ISC DHCP server configuration from NetBox data. This manual is for plugin {{VERSION}} and isc-dhcp-agent {{AGENT}}.

1. What the plugin does

From NetBox objects (tenants, prefixes, DNS servers) the plugin builds ISC DHCP files: the main dhcpd.conf, class and static host tables for tenant groups, and subnet files per pool type. Files are stored ready-made (with a SHA256 hash) and recomputed when the data changes. The DHCP server downloads and deploys them with isc-dhcp-agent (backup, test, restart, report back to NetBox).

2. Installation, update and requirements

Installing and updating the plugin is described in the README in the plugin repository (order: install the package, enable the plugin in PLUGINS in configuration.py, database migrations, restart NetBox and NetBox RQ). Migrations ship with the package – never run makemigrations on the server. An update never changes stored data. The plugin version and commit are shown top right on every plugin page.

The agent is installed on every DHCP server with the ready command from Plugin CFG → DHCP servers (chapter 17); later agent versions are installed from NetBox with the Update all agents button below the DHCP servers table.

3. Getting started step by step

This chapter is for a new user: what to prepare in NetBox, in which order to set up the plugin and how to get the CFG onto the DHCP server. Details of every page are in the following chapters. All values below are examples only – you choose the field names, groups and addresses yourself.

The whole flow: data in NetBox (prefixes, tenants, groups, custom fields) → the plugin builds files from them (dhcpd.conf, subnet files, group files) and stores them with a hash → isc-dhcp-agent on the DHCP server downloads them, backs up the old CFG, tests (dhcpd -t), restarts dhcpd and reports the result → NetBox shows the state and the Audit.

How the plugin reads NetBox data

The plugin has no network or device data of its own. It takes everything from three sources:

  1. Standard NetBox objects – prefixes (IPAM › Prefixes), tenants (Organization › Tenants), tenant groups (Organization › Tenant Groups). You already have them or create them the usual way.
  2. Custom fields you create in NetBox – data NetBox does not have by default: the device MAC address, the prefix pool type, whether a prefix goes to DHCP, a fixed IP. Without them the plugin has nothing to build DHCP from (explanation and steps below).
  3. Settings in the plugin – which fields are used, pool code, own variables, paths.

In the table names in <brackets> are placeholders – the real name is the value you enter. “Office” or “Printers” are only example values, not fixed plugin names.

Why custom fields are required

The plugin builds the DHCP server configuration only from data in NetBox. NetBox itself knows nothing about DHCP: a tenant has no field for a MAC address, a prefix does not know whether it is a DHCP pool or which code (ranges, lease, classes) to use. This data must exist as fields in NetBox – that is what custom fields are for. Without them the plugin has nothing to build DHCP from: no host, no subnet.

NetBox custom fields

  • Custom fields are created in NetBox (Customization › Custom Fields), not in the plugin. The admin chooses the name, type and object the field belongs to. The plugin only uses them.
  • The fields above (DHCP_POOL, POOL_TYPE, MAC1–MAC3, IP) are examples, not a fixed list. The plugin offers every field of the object (standard and custom) when selecting subnets (conditions, pool type field), in host sources (conditions, host name, MAC, IP) and in pool code as {{ cf.FIELD }}.
  • Example: a field DHCP_ROLE (Selection: PRINTER, WORKSTATION, SERVER, AP) on tenants or prefixes – use it in conditions or as the pool type.
  • Difference: a custom field = data stored on a NetBox object (e.g. a tenant's MAC, a prefix's pool type). An own variable (chapter 9) = a reusable piece of ISC DHCP configuration created in the plugin (e.g. lease times), put into code with USE <name>.

Setup in the plugin

The order matters: classes (e.g. "Office") come from host groups and a pool can use them only afterwards – the plugin refuses pool code with a class that does not exist. That is why hosts are set up before pools.

  1. Plugin CFG – language, base path (e.g. /opt/dhcp) and subdirectories (e.g. TABLE for groups and SUBNET for subnets). On the DHCP server dhcpd.conf is always in /etc/dhcp.
  2. DHCP-CFG › DNS servers – add 1–2 DNS servers and tick In use. Without DNS the warnings bar at the bottom shows a red warning.
  3. DHCP-CFG › Base dhcpd.conf – write the static part (global settings). The plugin never changes it, it only adds include lines below it. Example: 
    authoritative;
default-lease-time 3600;
max-lease-time 7200;
log-facility local7;
  4. DHCP-CFG › Own variables (optional) – e.g. description LEASE_8H, option default + max lease, value 28800. The pool code then needs just the line USE LEASE_8H.
  5. DHCP-CFG › Hosts and MAC addresses – card Table location: subdirectory TABLE. Card Table source: object Tenant group, name field Name. Switch on Write include lines of all group files into dhcpd.conf (classes are taken only from included files).
  6. In the Groups card click Set up at a group → Add source: object Tenant, condition Group = this group (without a condition the source selects nothing), host name field Name, host rows: MAC1 without IP (→ _Dynamic), optionally MAC2 with the IP field (→ _Static). The files Office_Dynamic and Office_Static and the class "Office" are created. Below you see the result and the summary “N hosts will not go to DHCP” with reasons; the class is “unused” so far.
  7. DHCP-CFG › Subnets – object IPAM › Prefix, subdirectory SUBNET. Add field DHCP_POOL → click the row → tick YES → Save. Add field POOL_TYPE and switch on Pool type (this field decides the pool type). Choose the gateway (first / last usable IP). Below the conditions you see “Selected: N objects”.
  8. Pools – the Subnets page gets one pool per POOL_TYPE value. Set up → write the code, look at the preview on a real prefix, set Use for (prefix sizes, e.g. /24 – /22) and switch on Generate. Saving checks the code on all subnets of the pool (also that the class exists). Example code: 
    subnet {{ network }} netmask {{ netmask }} {
    USE LEASE_8H
    option routers {{ gateway }};
    option domain-name-servers {{ dns|join(", ") }};
    pool {
        allow members of "Office";
        range {{ ip(10) }} {{ last_usable }};
    }
}
    Type ... to insert an allow members of line (list of existing classes), .. for a variable. The group page then shows the class as “used”.
  9. On the Subnets page switch on Write include lines of the subnet files into dhcpd.conf.
  10. DHCP-CFG › Files for the DHCP server – after the first installation click Regenerate all and check the file tree (dhcpd.conf with includes, TABLE, SUBNET). From then on files are recomputed by themselves on every change (only what the change touches).
  11. Plugin CFG › DHCP servers – Add server (name + IP or FQDN), Generate key, copy the install command and run it on the DHCP server (read the warnings in chapter 17 first; for a DHCP server that already runs also “Installing the agent on a DHCP server that already runs”). Within one interval the server is online, runs the current CFG number and the CFG control hash shows a green ✓ disk = NetBox.

Agent: what to check

  • On the server: sudo isc-dhcp-agent --show, sudo systemctl status isc-dhcp-agent, log /var/log/isc-dhcp-agent.log.
  • In NetBox at the server: online, agent version, ISC, dhcpd runs (pid), CFG number (green = current), ✓ disk = NetBox.
  • Control: Start / Stop / Restart dhcpd, Download again; below the table Update all agents (one button for every server with an older agent, switched-off ones too – a switched-off server gets only the agent update from NetBox, never a CFG). Everything is in the Audit.
  • A bad CFG: on an update the agent restores the backup and the previous CFG stays; on the very first NetBox CFG there is nothing to go back to – the bad CFG stays on disk without a restart (details in chapter 17, “What happens on an error”).

Installing the agent on a DHCP server that already runs

Back up the original DHCP yourself before installing the agent – this is the user's job. For example: sudo tar czf /root/dhcp-original.tgz /etc/dhcp /var/lib/dhcp /etc/default/isc-dhcp-server plus the files the original dhcpd.conf loads via include if they are outside /etc/dhcp.
  • Protection: when the agent has never deployed a NetBox CFG and finds another dhcpd.conf on the server, NetBox does not send the CFG. The server shows a frame “The agent found an original DHCP server” (whether dhcpd runs, the include files), a warning in the bar at the bottom and a red Audit row. The CFG is sent only after you tick “I have a backup of the original CFG and agree to overwrite the DHCP” and press Allow overwrite. The consent is in the Audit with a “waiting / the agent carried out the command” frame.
  • After the overwrite: dhcpd.conf comes from NetBox, the original is also in /opt/BCK/start_<time>/. The include files of the original CFG stay on disk but are no longer loaded. Leases stay.
  • Collision: if another tool manages the server (Ansible, own script, cron…), switch it off before installing the agent. The agent keeps NetBox as the source of truth and reverts foreign changes within 5 s, so the tools would fight. When the server's CFG changes outside NetBox 3 times or more in an hour, NetBox shows a red warning in the bar at the bottom (“another tool probably manages it too”).
  • Leases on a takeover: on its first run the agent at once (whatever the lease copy setting) copies the original leases to <backup dir>/leases/original_<time>/; the server shows “First run – copy of the original leases” (time, number of IPs, sha256, path) and the Audit has an INFO row. The agent keeps the newest 10 such copies (a test server makes more of them in simulations) and deletes older ones. On the overwrite itself (first NetBox CFG) the agent: stops dhcpd → copies the current leases into the backup → deploys and tests the CFG → starts dhcpd with the same leases → compares the number of IPs in the leases before and after the start. The server shows “leases kept N → N IP”; if there were fewer, a red warning with the path to the copy. The dynamic IPs stay as they were. The agent never restores leases by itself – an older copy would wipe newer assignments.
  • Tuning with DHCP off: after installing the agent you can stop dhcpd with Stop dhcpd (e.g. while another server serves DHCP). While dhcpd is stopped from NetBox the agent deploys and tests every CFG but does not start dhcpd (“CFG deployed and tested – dhcpd stays stopped”); start it with Start dhcpd.
  • Put the original leases back: after the first deployment the server has a button that brings back the leases from the agent's first run: CFG test → dhcpd stop → current leases to a backup (…/leases/before_restore_<time>/) → original leases back to /var/lib/dhcp/ → dhcpd start. The button is disabled until the NetBox CFG is deployed and tested OK on the server (or while the server waits for the overwrite consent). The agent takes the copy only from its own state, never from NetBox. Request and result are in the Audit frame; the server then shows “original leases put back – the server is fully managed by the agent and NetBox”. Note: IPs the server handed out after the agent was installed are lost – use it when another server served DHCP meanwhile.
  • Delete the original backup (agent 1.27.0): the agent reports whether the server still holds the backup of the original configuration (<backup dir>/start_<time>, made before the first NetBox CFG); NetBox shows it in the First run row with the number of files and the size. When the NetBox CFG runs (deployed, tested OK, dhcpd up) the button Delete the original backup (with a confirmation) deletes the copy of the original leases (original_<time>) and the original configuration backup. The agent deletes only these own dirs below /opt (paths from its own state, not from NetBox); other backups, the CFG and original dirs the agent did not create (e.g. an old configuration dir) stay – delete those by hand. The First run row then disappears and Put the original leases back is no longer possible. The result is in the Audit.
  • Test DHCP server (recommended): have a test DHCP server, make it First and switch on staged rollout. Try every new CFG and also the takeover of a server with an original DHCP on it first; the production servers get the CFG only after its OK.
  • Disk state (agent 1.25.0+): on every contact the agent sends the usage of the disks it writes to (backups, base path, leases, /). The server shows a Disk row with a label per disk: green up to 60 % (OK), yellow 60–85 % (clean up, e.g. old backups in /opt/BCK), red from 85 % (critical – backups and new CFG may fail to write). Yellow and red also appear in the warnings bar at the bottom of the plugin pages and every colour change is in the Audit.
  • Failed backup (agent 1.25.0+): when even one file cannot be backed up before a CFG is deployed (e.g. full disk), the agent changes nothing and reports an error (“BACKUP FAILED … nothing was changed”). The same for Put the original leases back: without a copy of the current leases nothing is overwritten and dhcpd is always started again. The agent keeps the newest 10 before_restore_<time> directories.
  • Contact interval: the agent accepts only 10 s – 30 min (other values are ignored).
  • Staged rollout with a test server (plugin 1.12.0): there can be only one test server. Every new CFG goes only to it: download → hash check → test → dhcpd start (if it was stopped from NetBox, NetBox starts it). When dhcpd runs 60 s and the disk hash = NetBox, the CFG is verified: dhcpd on the test server is stopped (Stop command from NetBox, in the Audit) and all production servers get the CFG at once (usual hash check + test). When the CFG already runs fine on some server (e.g. the test server was switched off), the production servers do not wait for the test server; the test server fetches the CFG, tests it, starts dhcpd and stops it at once (no 60 s wait). When the test server holds the CFG but it is not verified and dhcpd is stopped from NetBox, NetBox starts it for the check and stops it again (Audit INFO). When it fails on the test server, the production servers get nothing (no Let the next go button) – fixing the CFG is the admin's job. The test server shows a CFG check row (verified / checking / failed). Without a test server and Staged rollout on, the CFG goes to First and then in order, each after the previous one's OK. The tree description is in Plugin settings below the Staged rollout switch (“How it works”). While a test server is on, the First switch and Staged rollout are not used and not shown – the text “The order is driven by the test server …” is shown instead; the test server never waits for production servers. When the test server is switched off with at least two servers enabled, NetBox asks which server goes first (pick + Switch the test off); with one server it does not ask. The switch Keep the new CFG on a failed test applies only to the test server; production servers always restore the backup.
  • Start dhcpd on the test server (plugin 1.12.1): the Start dhcpd button opens “How long should dhcpd run?” – 5 / 10 / 20 / 40 / 60 / 120 min. The server shows “dhcpd stops at HH:MM · left mm:ss” (countdown). When the time is up NetBox stops it (at the next contact of the agent, Audit INFO); While it runs, the Change time button at the countdown sets a new time (5–120 min, counted from now). Stop dhcpd stops it at once. When dhcpd goes down in any way (Stop, by hand, crash) the timer ends; a new or failed CFG does not change the timer (the CFG check does not stop dhcpd while the timer runs). dhcpd stopped from NetBox is a blue info warning in the bar at the bottom (not a fault) and a yellow INFO row in the Audit (not WARNING) with the reason: run time up, the test server verified the CFG, or the Stop dhcpd button (who).
  • Server reboot (agent 1.26.0): the agent detects a reboot by the boot ID. dhcpd started by the system after a reboot is reported as a normal start (Audit INFO “the server was rebooted – dhcpd started by the system as usual”), not as a manual restart. The test server that was stopped from NetBox before the reboot is stopped again by the agent (INFO with the reason). Production servers are always left running. dhcpd not running after a reboot is a WARNING.
  • Agent page (menu ISC DHCP → Agent, read only): the commands the agent uses (test dhcpd -t -cf /etc/dhcp/dhcpd.conf, restart systemctl restart isc-dhcp-server, service start/stop), the fixed list of commands NetBox may send to it and what the agent does by itself. Nothing can be changed there; only the Backup directory stayed in Plugin settings.
  • Agent settings (agent 1.30.0): the Agent settings page (link in Plugin settings at the Agent interval and on the Agent page) and the API /api/plugins/isc-dhcp/agent/settings/ (logged-in user or API token) show for every agent what NetBox sends and what the agent reports it really uses (interval, lease copy, date format, test server) – matches / does not match – plus its local settings from /etc/isc-dhcp-agent.conf. The agent sends it every 1 / 5 / 10 / 20 min (Agent settings check in Plugin settings) and right after every change. A settings change reaches the agent at its next contact (Agent interval). A switched-off server gets the settings too, never a CFG.
  • CFG changed outside NetBox (agent 1.29.0): after every successful deployment the agent keeps a copy of the running CFG in <backup dir>/_current (root only, read-only, with the control hash confirmed by NetBox). When a CFG file on the server is changed outside the agent: NetBox reachable = the files are downloaded from NetBox; NetBox not reachable = the files are put back from _current (changed ones overwritten, added ones removed, missing ones restored). When it is the same CFG dhcpd already runs, dhcpd is not restarted. When the _current copy was changed too, the agent restores nothing and logs it. The event is in the Audit after the next contact with NetBox.
  • Production server (protection): the Production switch at the DHCP server (off by default, the admin switches it on). While on, the name has a PRODUCTION label, NetBox never sends it Stop dhcpd (the button is disabled) and it cannot become the test server; restart and new CFG work as usual. Switching the protection off must be confirmed (I understand) and is logged in the Audit. Test and production exclude each other.
  • Test server in NetBox: switch on Test server at the DHCP server – the name gets a TEST label and the server becomes First (only when it may be First: agent online, the same ISC version as the other servers – otherwise the order stays and the reason is shown) (a new CFG goes there first). Nothing has to be set on the server – this switch is enough. The server then has the button Test – simulate the first run: the agent clears its state (files stay) and acts as on a first installation – copy of the original leases, waiting for Allow overwrite, after the consent dhcpd stop → leases copy → CFG deployment and test → dhcpd start → leases check. The result is one Audit row with collapsible output (and the frame at the command). On a production server it can be forbidden for good locally: sudo isc-dhcp-agent --set TEST_SERVER no – the agent then refuses it (SECURITY in the log) whatever NetBox says.
  • Safe order: prepare the CFG in NetBox to match the original → back up → add the server (it may be switched off, then the agent gets nothing) → install the agent → check the frame at the server → allow the overwrite at a quiet time.

10. Hosts and MAC addresses

Page DHCP-CFG › Hosts and MAC addresses. Everything is set by clicking:

  1. Table location – the table subdirectory (full path shown, e.g. /opt/dhcp/TABLE/).
  2. Table source (groups) – a tree: the object whose every item (e.g. Tenant group) gets two files <Name>_Dynamic and <Name>_Static, and the name field (built-in or custom field, usually Name). Turn off a group you do not want with the switch in the groups list.
  3. Code templates – deleting: a template shows “used in N groups, in the CFG for the DHCP servers M” (only groups of the current table source). A template cannot be deleted while files that go to the DHCP servers are made from it. Groups without generated files do not block it, they get another template of the same kind. The last template of a kind that a group uses cannot be deleted.
  4. Table source – at most 100 items: every item of the object is one DHCP class (2 files). An object with more than 100 items (e.g. Tenant instead of Tenant group) cannot be saved; if it is already stored, no groups are created and the table files stay unchanged until you pick the right object. The number of hosts in the groups and the number of subnets are not limited by this.
  5. Groups (tables) – a list like the pools: On / Off switch, number of objects, files with full path, sources, MAC counts and warnings. A group switched off still has its files, but without MAC addresses – base configuration only, so DHCP does not fail. Set up opens the group page.
  6. Group page – at the top the summary "N hosts will not get into DHCP" (no MAC, no IP, invalid MAC/IP, name not allowed, same host name) and the warnings; both expand on click. The group is turned on / off only in the groups list.
    • Host sources (Add source): object (e.g. Tenant, Device), conditions on an internal field or custom field (which objects; like on Subnets) and the host name field.
    • Hosts of one object (no limit of rows; every MAC field at most once in _Dynamic and once in _Static, every IP field once): every row = MAC field + IP field (optional). A row without an IP field always goes to _Dynamic (class match). A row with an IP field goes to _Static (host block); the Also into class switch (shown only with an IP field) puts the same MAC into _Dynamic too, so the device gets an IP in another pool (otherwise MismatchClient). If the IP field is empty (or invalid), the host cannot be static: with “Also into class” it goes to _Dynamic only, without it it does not get into DHCP (summary “no IP”). The same MAC field may be in two rows only as one static row (without “Also into class”) + one row without IP (Dynamic); twice in Static or twice in Dynamic is refused with an explanation (duplicate hosts). Every field can be used once. Column Goes to: Dynamic / Static / Static + Dynamic.
    • only without IP (checkbox at the IP field): ticked = the row goes to _Dynamic and takes only objects without an IP in that field; unticked = Static. Can be toggled in the table too. The MAC is always required.
    • Names: one row = NAME, more rows = NAME_1, NAME_2… by row order. Two host blocks with the same name are never made; a duplicate MAC or IP is only a warning.
    • Include: both files show whether they are included in dhcpd.conf (include written by the plugin or in the static part); without include the DHCP server does not read them.
    • Class usage: at the _Dynamic file the plugin shows every defined class (e.g. the group, MismatchedClients) – where it is used (allow / deny members of "…" in pool codes, individual subnet codes and the static part of dhcpd.conf) and in how many subnets; an unused class = warning (the DHCP server ignores it). The groups list has a Usage column.
    • option host-name (static row): NAME (default), NAME_n (as the host block name), another field of the object or leave out.
    • Files: path, suffix (_Dynamic / _Static, editable), host count and Show CFG = preview of the finished file from real data; the MAC/IP list expands on click.

Code templates (card 4 on the Hosts page): a library of file codes (name, kind Dynamic / Static, Jinja code). After installation there are 2 simple ones: Dynamic = class with match hardware + a subclass per MAC, Static = host blocks. A template used by a group cannot be deleted. Static: several MACs of one object = host blocks NAME_1, NAME_2, NAME_3; one MAC = NAME.

File code – in a group you pick a template for each file or one of the group’s own codes. Edited code is saved as an own code with a name (description), unique within the group; a group may keep several and uses the selected one. Saving needs “I understand” ticked. Switching to a template does not delete own code, it is just unused; unused own code can be deleted. On the Hosts page each template shows a tree of groups using own code (“+N locally edited”); code is per group (like a pool), on the group page at each file (Code, expands on click); the groups list marks edited code. Jinja code for _Dynamic (variables class_name, pairs, tenants) and _Static (class_name, hosts: h.host, h.mac, h.ip, h.name, h.hostname). State default / edited, Restore default. Bad code is not saved (the draft stays in the editor). A group switched off has an empty class (match if false;) and no host blocks.

Next step: storing the files (SHA256) and including them in dhcpd.conf.

Classes

Classes are created by the groups' _Dynamic files in Hosts and MAC addresses (only those included in dhcpd.conf). The Subnets page shows a class card with their use in pools. Subnet code with allow/deny members of "X" where class X does not exist is refused (dhcpd would not start) and such a subnet is not exported. .. in subnet code offers an allow/deny line for every dynamic class.

Class protection: renaming a group (the NetBox object) renames the class in every subnet code and in the static part too (only allow/deny/ignore members of lines). A group whose class is used cannot be deleted in NetBox; a plugin change after which a used class would disappear (group/table include, own code, template) is saved only after a confirmation: right below the row you clicked a box lists the classes and where they are used (the Hosts page and the group page save in the background, without a page reload), tick I understand, do it anyway and Apply the change. Subnets whose code uses the missing class then become incompatible and stay out of the CFG until you change their code (dhcpd would not start with a missing class). .. = own variables (yellow, USE name); ... = dynamic classes (blue): inserts ## CLASS ADDED VIA DYNAMIC CLASSES + USE ALLOW X / USE DENY X, which becomes allow members of "X"; ## added via dynamic class X ## in the CFG. Hand-written allow/deny members of "X" with a dynamic class show a yellow hint with a Replace all button (count per pool on Subnets).

Where classes are used: Hosts → the Usage column has an arrow ▸; expanded: the _Dynamic file, the class and per pool (or individual code) allow/deny and the number of generated subnet CFGs containing it. Subnets → pools table, column Uses ▸: classes (USE blue / by hand, the _Dynamic file creating them) and own variables (yellow).

12. Pool code check

On every save the plugin tries the code on all prefixes of the pool. If it finds an error, the code is not saved (the last working code stays), the errors are listed with the number of prefixes and an example, and your text stays in the editor. Checked:

  • everything is inside one subnet <network> netmask <mask> { } block, network and mask match the prefix,
  • ; at the end of statements, closed quotes, parentheses and { },
  • unknown or misspelled statements and options (standard ISC options + own options from the static part option X code N),
  • the same option twice in one block,
  • values: IP addresses (routers, DNS, NTP…), numbers (lease times), quoted text (domain-name, filename…),
  • option routers on subnet level must be a usable address, option subnet-mask must match the mask, default-lease-time must not exceed max-lease-time,
  • classes in allow/deny members of "X" must exist (tenant tables or static part),
  • words in log (...) expressions – e.g. foo must be defined with set foo = … in the static part,
  • range inside the network, not overlapping, gateway outside ranges, ip(n) within usable addresses, unknown USE.
The check does not replace dhcpd -t on the DHCP server, but it catches the common errors that would stop the DHCP server from starting.

13. Pool sizes and incompatible subnets

  • Code is suitable for – on save the plugin tries the code on sizes /16 to /30 and shows which work (e.g. /16 – /27).
  • Use for – narrow where the code is used (e.g. only /24). It cannot exceed the suitable range; "auto" = the whole suitable range.
  • A subnet whose size is outside the range (e.g. changed from /24 to /28 in NetBox) or that the code does not fit is incompatible: it is not exported and the DHCP server keeps running without it.
  • The bar at the bottom of every plugin page then shows a red warning; the list with reasons is on the Subnets page and on the pool, and the pools table shows a red count.
  • Incompatible subnets do not block saving the code – only subnets within the range are checked.

  • Changes of the pool code do not affect individual subnets – on save the plugin lists which subnets are not affected.

15. Files for the DHCP server

  • DHCP-CFG → Files for the DHCP server: directory and file tree exactly as the DHCP server gets it (dhcpd.conf, TABLE, SUBNET) with size, SHA256 and change time; click a file to see its content.
  • Files are stored in advance. A change in NetBox recomputes only what it touches (a PC = only its group's files, a prefix = only its subnet, a pool = only its subnets), then dhcpd.conf. dhcpd.conf includes = exactly the stored files.
  • Manifest dhcp/export/manifest.json: set hash, directories and files (path, SHA256, size, time). File: dhcp/export/file/<path> (plain text, X-SHA256 header).
  • Without login only the DHCP servers from Plugin settings → DHCP servers. Regenerate all creates all files again.
  • Manual distribution (the admin's own script): downloads the manifest, compares SHA256, downloads new/changed files, then dhcpd.conf, tests (dhcpd -t), restarts the service, finally deletes files missing in the manifest (only in the manifest's directories).

Two ways to distribute the CFG – alternatives:

Manual (own script)Automatic (isc-dhcp-agent)
The admin uses the manifest and files (or the API) and an own script, and takes care of download, SHA256 check, test, backup, deployment and restart. NetBox does not know whether and how the CFG was deployed. The agent talks to NetBox, downloads only changes, backs up, tests, restarts dhcpd, restores the backup on an error and reports the result to NetBox (server state, Audit).

Use only one way per server. The agent keeps the CFG as in NetBox and reverts changes by another tool within 5 s – an own script (or Ansible, cron…) on the same files would collide with it.

Restart, not reload: ISC dhcpd cannot load a new configuration while running (reload); a new CFG is always deployed by restarting the service.

16. Audit and DHCP servers

  • Plugin settings → DHCP servers: name + IP or FQDN (resolved to IP, refreshed every 5 minutes), enabled switch. Only these servers can download the manifest and files without login; a logged-in admin always can.
  • Audit (directly in the plugin menu): every generation (time, who, cause – e.g. “tenant “PC1” saved”, button, plugin update –, duration, changed files +added ~changed −deleted with diff) and every download (server IP, manifest, files). Filter by type, last 10,000 records.

17. isc-dhcp-agent (operation)

Before installing the agent – what it changes in the system (on by default):
  • DEFAULT_FIX=yes: checks /etc/default/isc-dhcp-server; when the file is missing, INTERFACESv4 is empty or INTERFACESv6 is set it creates/fills the IPv4 interfaces, sets INTERFACESv6="" (original kept as .bak-agent) and disables and masks a separate isc-dhcp-server6 service. Switch it off on servers with DHCPv6.
  • APPARMOR_FIX=yes: adds a local AppArmor rule (/etc/apparmor.d/local/usr.sbin.dhcpd) so dhcpd can read the files below the base path, and reloads the profile.
  • ALLOW_HTTP=yes: when https does not work the agent also tries http – the API key and the CFG then travel unencrypted (the server shows a red “http – unencrypted”). We recommend forbidding http in production.
Switch off (on the DHCP server, root): sudo isc-dhcp-agent --set DEFAULT_FIX no, sudo isc-dhcp-agent --set APPARMOR_FIX no, sudo isc-dhcp-agent --set ALLOW_HTTP no. Keep this in mind especially on existing production servers and with IPv6.
  • Install on every DHCP server (root): copy the ready command with the address and the key in Plugin CFG → DHCP servers → Agent install command. Installs /usr/local/sbin/isc-dhcp-agent, /etc/isc-dhcp-agent.conf and the service isc-dhcp-agent (systemd, auto restart). Needs only curl, sha256sum, flock (no jq). Uninstall: install.sh --uninstall. Log: /var/log/isc-dhcp-agent.log (also journalctl -u isc-dhcp-agent).
  • The server must be in Plugin settings → DHCP servers (by IP). Everything else is controlled by NetBox: interval (10 s – 30 min), paths (dhcpd.conf always in the fixed /etc/dhcp, the rest by base path and subdirectories), backup dir (default /opt/BCK), test and restart commands.
  • Flow: the agent sends the control hash of its CFG files (the file list with sha256 only on a mismatch) → gets only changes and files to delete → downloads them and checks sha256 (nothing changes on mismatch) → backup = cp of the files that will be replaced or deleted + the leases to /opt/BCK/<CFG number>_<time> (last 10) → installs (dhcpd.conf last) → test → restart and check dhcpd runs → deletes unused files → reports OK. Results on an error are in the table below.
  • CFG number: every new set of files gets dd.mm.yy_NNN (e.g. 18.11.26_003). Each server shows which CFG runs; a mismatch with the current one shows “CFG mismatch”. When servers run different CFGs, a new CFG goes to the First server only, the others after its OK.
  • A failed CFG is never sent again to the server where it failed (no loop) – it waits for a new CFG. If the problem was the server (not the CFG): Download again. If a silent server blocks the others: Let the next go.
  • ISC version – requirement: all DHCP servers must run the same ISC dhcpd version. It is a limit of the staged rollout: the same CFG is verified on one server and only then goes to the others – which only makes sense with the same dhcpd. The agent reports the version at every contact. On a difference: a red warning in the bar at the bottom, only the First server gets the CFG, the other servers wait (“waiting – different ISC versions, CFG goes to First only”) and keep running their current CFG; the First switch cannot be changed. The admin must make the ISC version the same on all servers (update / change the isc-dhcp-server package). At the next contact the agent reports the new version, the wait ends by itself and the waiting servers get the CFG (in order with staged rollout on). Without ISC installed the agent runs, reports “ISC DHCP is not installed” and gets no CFG.
  • Safety: the agent runs the test/restart command from NetBox only when it is also allowed in /etc/isc-dhcp-agent.conf (ALLOWED_TEST_CMDS / ALLOWED_RESTART_CMDS); otherwise the local one is used and the report says so. It writes and deletes only below the base path and dhcpd.conf in /etc/dhcp.
  • Per server: last contact (red when silent for 3× interval), ISC and agent version, running CFG, last report. Audit: plans, reports (test output), agent state changes (version, dhcpd running or not, first contact) and every change of DHCP servers and agent settings (who, from where, old → new).

Manual (PDF) opens from every plugin page (top right), in the plugin language (SK / EN).

Real dhcpd state (agent 1.9.5+): dhcpd runs only when the service is active and a dhcpd process exists. Service “failed” with a dhcpd process = not running; service “active” without a process (crash) = not running. Before every start/restart the agent ends a dhcpd process outside the service, removes a stale pidfile (left after a crash or kill, it blocks a clean start) and resets the failed state.

Why dhcpd stopped / started outside the agent (agent 1.10.0+): the agent reads the system journal since the last contact: a command via sudo (user + command), systemctl/service as root, a kernel crash (segfault, out of memory) or a crash/kill without a stop command. The reason is shown at the server in the Service row (yellow = command, red = crash), in the Audit and in the agent log. The event is never lost when NetBox is unreachable (503) – the agent sends it at the first successful contact.

dhcpd will not start although the CFG is OK (agent 1.11.0+): when dhcpd -t passes but the service does not start (e.g. the IPv6 server dhcpd6 fails and takes the whole service down), NetBox does not report it as a CFG error. The server shows an orange "dhcpd did not start – retrying every minute". The agent retries every minute until dhcpd is up whenever the disk has the current CFG and dhcpd is down (after a Start/Restart command, after a crash, and after an agent update – no clicking needed): test the CFG → check for a dhcpd outside the service → kill it → remove the stale pidfile → start. It stops only when dhcpd runs, when you press Stop, or when a new CFG arrives. If dhcpd -t now fails, it is a CFG error and the agent stops retrying.

dhcpd PID: the agent sends the running dhcpd PID to NetBox (the server shows "runs · pid XXXX") and to the Audit, and before every action (start, stop, restart, killing a process) it logs the transition "dhcpd PID: X -> Y".

dhcpd and service state (agent 1.12.0+): “dhcpd runs” = an IPv4 dhcpd process runs, so DHCP is really served. The service state (systemctl: active / failed / …) is reported separately with the reason from the journal – a yellow line at the server “service isc-dhcp-server is failed” + the error (e.g. dhcpd6 … failed! = the IPv6 server the service starts together with IPv4 fails) and a yellow bar on top. The agent never kills a running dhcpd by itself; only your Start / Restart / Stop does. When something does not work the agent runs a full check and writes it to the log and the Audit: last NetBox command, service state, every dhcpd process (in the service / outside it), pidfile (alive / dead), service error. When the agent reports dhcpd running the current CFG, an old “failed” report is cleared (a real dhcpd -t failure stays).

IPv6 (dhcpd6): without /etc/default/isc-dhcp-server or with an empty INTERFACESv4="" the Debian init script starts the IPv4 and the IPv6 server. IPv6 without subnet6 fails (“No subnet6 declaration … Not configured to listen on any interfaces!”) and the service is failed although IPv4 DHCP runs. The agent shows this at the server with the fix: create the file (or fill the empty line) with INTERFACESv4="<interface>" and INTERFACESv6="". The Restart dhcpd button does a real restart even when dhcpd runs.

Several dhcpd at once (agent 1.12.3+): when two or more IPv4 dhcpd run (e.g. two restarts at the same moment), the agent ends all of them, removes the pidfile and starts one clean through the service (stays down after Stop from NetBox), logs “dhcpd PID: A B -> C” and the Audit shows “several dhcpd ran at once”.

The agent fixes the service settings (agent 1.13.0+, DEFAULT_FIX=yes): on every contact it checks /etc/default/isc-dhcp-server. When the file is missing, INTERFACESv4 is empty or INTERFACESv6 is set, the agent fixes it: INTERFACESv4 = every interface with an IPv4 address (filled interfaces are kept), INTERFACESv6="" (IPv6 server off for good). The original file is kept as .bak-agent. A separate isc-dhcp-server6 unit is disabled and masked. When the service was not OK, it is restarted (not after Stop from NetBox). The change is in the agent log and the Audit (“the agent fixed a server setting”). Switch off: DEFAULT_FIX=no in /etc/isc-dhcp-agent.conf.

Agent security (agent 1.14.0+): Addresses: the agent tries the set address (any port), then the same port with the other scheme, then 443 (https) and 80 (http); the first one that works is saved. From http it tries https every hour. Over http the server shows a red “http – unencrypted” and a bar on top – the key and the CFG travel in the clear; http can be forbidden (ALLOW_HTTP=no). Every URL NetBox sends (files, bundle, report, update) is always used on the agent's own NetBox address – the key is never sent to another host. Paths: the dhcpd.conf directory is fixed to /etc/dhcp on the server (DHCP_CONF_DIR). The base path is pinned at the first contact (ALLOWED_BASE in /etc/isc-dhcp-agent.conf); a different one from NetBox is refused and reported (allow it with isc-dhcp-agent --set ALLOWED_BASE /new/path). System directories (/, /etc, /usr, /root…) are refused by the agent and NetBox. Deletes only below the base path. Bundle: a tar.gz with links (symlinks) or special files is refused. Key: the full key and the install command are shown only to users who may change Plugin CFG; a key in a bad format is ignored by the agent.

DHCP server stopped / started outside NetBox (agent 1.14.1+): when someone stops or starts dhcpd on the server itself (systemctl, service, kill), the Audit has its own row with the badge OUTSIDE NETBOX: “DHCP server (dhcpd) STOPPED on the server itself – the command did NOT go through NetBox” + how (sudo with the user name, a root command, a kernel crash, kill) and for a root command also who was logged in at that moment (user, terminal, IP). The agent then starts dhcpd again (“dhcpd started again by the agent automatically”). To keep it down, use Stop dhcpd in NetBox – the Audit then says “dhcpd stopped by the agent on a NetBox command”.

Warnings are on every plugin page in the bar at the bottom (pinned, visible while scrolling; only the version and the manual stay at the top). The collapsed bar is 1 line: the warnings scroll from right to left (the mouse stops them), at the right are coloured counts (red / yellow / blue) and “N warnings”. A click on “N warnings” expands 1 line per warning (red first); long text scrolls inside its line, links are at the right, lists have a “Show tree” button. Whether the bar is collapsed or expanded when a page opens is set in Plugin CFG → Warnings at the bottom of the pages. The bar refreshes itself every 10 s – no page reload needed. New value on Subnets: when a field of a condition on the Subnets page (e.g. pool type, DHCP_POOL) gets a value that is not ticked (e.g. a new tenant group), the bar shows a blue warning with the number of prefixes that have it and what is missing (set it on prefixes / tick it on Subnets). Show tree lists exactly those prefixes (linked to the prefix in NetBox) that have this value and match the other conditions. The Do not use button stops reporting it; it can be undone on Subnets in the expanded row of the field (“report again”). CFG number is DD.MM.YY_NNN, the first CFG of the day is _001.

Audit colours: every row has a label and a coloured edge – OK (green: new CFG runs, dhcpd runs, download, generation), INFO (yellow: agent update, settings changed by an admin, NetBox command, the agent fixed a setting or started dhcpd again), WARNING (red, whole row tinted: dhcpd down, stopped outside NetBox, service failed, CFG error, dhcpd did not start, unencrypted http, refused access, several dhcpd at once, failed command).

Backups and deleting (agent 1.15.0+, plugin 1.0.0): the backup directory must be below /opt/ (default /opt/BCK). NetBox does not save another one and the agent refuses it (uses /opt/BCK and logs SECURITY). The agent deletes (rm -rf) only its own old backups named <CFG number>_<YYYYmmdd-HHMMSS> in that directory (keeps the newest 10); other files and directories there are left alone. Otherwise it deletes only CFG files below the base path (files the plugin no longer generates) and new files when restoring a backup. Locally also: its own state files, its own temp directory and a dead dhcpd pidfile, only in /run.

Command list (Plugin CFG → DHCP servers → Commands NetBox can send to the agent, collapsible, cannot be changed): fixed list of everything NetBox sends to the agent (download, bundle, backup, test, restart, delete, Start/Stop/Restart, update, key, interval, paths, info), each with what the agent does and its limit. The list is the same (1:1) in the plugin and in the agent, a test checks it. A line not in the list is not run; the agent logs "SECURITY … ignored". Test and restart run only commands allowed locally in /etc/isc-dhcp-agent.conf (ALLOWED_TEST_CMDS, ALLOWED_RESTART_CMDS). Below the list: what the agent does on its own (/etc/default fix, AppArmor, ending dhcpd outside the service, repeated start, pidfile). The agent sends NetBox only text state. The key goes to curl from a root-only file (/var/lib/isc-dhcp-agent/auth.hdr), it is then not visible in the process list (ps). This holds only when running as root with curl 7.55+; with an older curl the agent passes the key as a curl argument and it may be visible in ps.

Auto CFG sync (plugin 1.1.0, Plugin CFG → DHCP servers): when a server runs another CFG than NetBox (“older – NetBox has …” at the server), NetBox pushes the full CFG by itself (like the Download again button). Options: Off (default), After X minutes of mismatch (5 / 15 / 30 / 60 min; a next mismatch not sooner than X min later) or Daily at a fixed time (e.g. 03:00, once a day). The server shows “auto sync at HH:MM”. A good CFG is applied and the server is “current”. A bad CFG: the test fails, the agent restores the backup and the original CFG stays; the server shows “the new CFG failed here – the original stays” and the same bad CFG is not sent again automatically (only a fixed one, or Download again by hand). Never after Stop from NetBox, during staged rollout (waiting for another server) or without ISC. Every sync is in the Audit as yellow INFO “NetBox auto-synced the CFG…”.

CFG control hash (agent 1.16.0+, plugin 1.2.0, Plugin CFG → DHCP servers, below Auto CFG sync): one hash of all CFG files (sorted lines “path sha256”, sha256 of them). NetBox computes it from its files, the agent from the files on the server's disk. On every contact the agent first sends only this hash: equal = the disk is exactly NetBox's CFG, nothing more is sent; different = the first sign that something is wrong – the agent sends its file list at once and NetBox makes the plan from it (what to download, what to delete). Each server shows “disk = NetBox” (green) or “disk ≠ NetBox” (red) with the disk hash. Shortly after a change in NetBox a mismatch is normal until the agent downloads the new CFG. A file changed by hand on the server shows as a mismatch and the agent repairs it.

Changes outside NetBox (agent 1.17.1+, plugin 1.3.1): NetBox is the source of truth. Between contacts the agent watches dhcpd (PID, running) every 5 s and computes the control hash of the CFG files (nothing is missed, editor temp files raise no alarm). When the agent restarts dhcpd itself (e.g. restoring a file), the server shows “agent” again, not “by hand”. When someone restarts dhcpd by hand or changes a CFG file, the agent computes the control hash and contacts NetBox at once (no waiting for the interval). The Audit gets a red OUTSIDE NETBOX row: “dhcpd RESTARTED on the server itself (PID X → Y)” with the journal reason, or “CFG on the server CHANGED outside NetBox” with the file list (changed / missing / extra). The agent then downloads only the files that differ, tests them and restarts dhcpd. Editor files (.*, *~) are not watched.

Leases (/var/lib/dhcp/dhcpd.leases, the database of given IPs): copied into the backup (<backup>/_leases/) before every restart. A backup restore never puts them back (old leases = the same IP for two devices) and the agent never deletes them. The copy is for a manual restore when the server dies. Other path: LEASES_FILE in /etc/isc-dhcp-agent.conf. Periodic lease copy (plugin 1.4.0, agent 1.18.0+, Plugin CFG → DHCP servers → Lease copy): set in NetBox, the agent takes the setting at every contact (nothing to set on the server). Every N minutes (default 1 h) – by the clock, at the same minute on every server (1 h = always at xx:00, 30 min = xx:00 and xx:30; agent 1.28.0) – the agent copies the leases to its own directory <backup dir>/leases/<date-time>/ with the original file names (dhcpd.leases, dhcpd.leases~; only below /opt) and keeps the newest K copies (default 72 = 3 days, covers a weekend). An unchanged file is not copied again. Every new setting from NetBox (lease copy, date format, interval) is written to the agent log (“setting from NetBox: …”) and the Audit has an Admin row with what changed (old → new value). For a command (Start / Stop / Restart dhcpd, Update all agents) and for a change of the lease copy, the date format or the interval the row has a frame with every server: “Agent DHCP: <server> – waiting for the agent”, then “… – the agent carried out the command <time>” (or “the agent FAILED to carry out the command” with the reason); the Agent label has the colour of the Type column. The command result is only in this frame (the agent row does not repeat it). Changing these settings does not regenerate the CFG, saving is instant. The set date and time format (DAY.MONTH.YEAR-HOUR:MIN, YEAR-MONTH-DAY_HOUR:MIN, YEARMONTHDAY-HOURMINSEC) is used for the Audit time too (with seconds). Only its own copy directories are deleted. The date and time format of the directories is set there too: DAY.MONTH.YEAR-HOUR:MIN (default, e.g. 20.11.2026-20:14), YEAR-MONTH-DAY_HOUR:MIN or YEARMONTHDAY-HOURMINSEC. After a format change the agent on every server renames the existing copy directories by itself (old copies dhcpd.leases_<time> are moved into directories too). The server shows a Leases row “copy current as of …” in the set date and time format, with the sha256 of the newest copy (yellow when older than twice the interval). Every new copy is a yellow INFO row in the Audit: “the agent backed up dhcpd.leases → leases/<date-time>/ – the hash changed from … to …”.

Appendix: agent API (technical)

  • Technical description of the API used by isc-dhcp-agent (not needed for normal use). The server must be in Plugin settings → DHCP servers (recognised by IP). There are also Agent commands, shared by all servers: test (default dhcpd -t -cf {conf}), restart (default systemctl restart isc-dhcp-server; ISC dhcpd has no reload, always restart) and the backup directory.
  • Agent mode (shared by all servers, Plugin settings → DHCP servers): Plan = only changes based on what the server says it has; Export = download everything (only when the set changed since the server's last OK report). Backup is the script's job.
  • A server that has not reported OK yet always gets the complete CFG; only after the first OK does it get just changes in Plan mode.
  • Staged rollout (optional): the server marked by the First switch (always just one) gets a new CFG first, then the others in list order (which never changes); the next one only after the previous reported OK for the same set – until then it gets empty steps and wait_for with the server names it waits for.
  • 1. Steps: GET or POST dhcp/export/agent/ with JSON {"files": {"/path": "sha256", …}} (what the server has in the managed directories + dhcpd.conf). Agent 1.16.0+ also sends disk_hash (control hash) and, when it equals check from the last answer, only nofiles=1 without the file list. Answer {"hash", "server", "steps": [...]}; empty steps = do nothing.
  • Steps (run in order, field step = number): backup (paths → to), download (url, path, sha256: download to a temp file, verify SHA256, move to path; dhcpd.conf always last), test (cmd; on error restore the backup = on_fail restore), restart (cmd; if dhcpd does not run, restore and restart), delete (path: only files of the managed directories, after a successful restart), report.
  • 2. Report: POST dhcp/export/report/ with JSON {"hash", "result": "ok"|"test_failed"|"rolled_back"|"failed", "output": "dhcpd -t output / error", "done": [step numbers]}. The server state is in plugin settings (last report, hash, ✓ = has the current set), every plan and report in the Audit.
  • If dhcpd.conf is not generated (path missing), the plan returns error 409 and the agent must do nothing.
